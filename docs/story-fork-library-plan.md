# 故事知识库分支（fork）功能 · 初步规划

> 状态：**初步构想，非执行规格**。主线仍是资料提取重构（见 `material-extraction-refactor-plan.md`）。
> 本文档仅勾勒方向、边界与依赖，待资料提取重构 **D14** 落地后再升级为可执行的细化方案。
> 用户约定的"活文档"规则同样适用：后续讨论发现不足随时回填并在变更记录追加。

---

## 1. 目标

支持"共享原著库 + 每故事 fork 一份 COW 副本"的使用模型：

- 原著 canon 抽入**共享原著库**（项目作用域），所有故事可引用同一份；
- 每个故事建好时，从共享库**复制一份到自己名下**，副本上可随意增改，不影响原库；
- 一个故事可继承**多个**原著库的副本（无限流：多部独立原著各成世界）。

---

## 2. 与资料提取重构的关系

- **前置依赖：D14**（导入原著 canon 打 `setting_scope="project"` + `story_id=""`，放进共享库）。
  D14 未完成前，canon 卡在单一 story 作用域（`source_workflows.py:591`），无法被多故事共享，fork 也无正确源头。
- **本功能不在资料提取重构范围内**：它是"建故事 / 读取"侧的能力，资料提取只负责把正确的 canon 喂进共享库。
- 资料提取重构已把本功能标为 **D15（下游，refactor 2「库绑定」）**，此处先独立列出初步构想，不展开实现。

---

## 3. 核心设计（基于已核实的现有机制，零 schema 改动）

- **层级用 `setting_scope` 维度建模**：`knowledge_items` 已含 `setting_scope` / `story_id`（迁移 001:127-153）；`isolation_domain`（`entity_identity.py:57`）= `(setting_scope, story_id, worldline_id, version_scope)`，且非 story 作用域自动清空 story_id → `project`（库）与 `story`（fork）天然分层。
- **fork 操作 = COW 复制**：`fork_library_to_story(project_name, story_id, source_ids)` 把 `project` 作用域的 canon 条目复制到 `story` 作用域，带 `forked_from_library_id` 溯源；复用现有 `clone_story_storage_rows` 思路。
- **隔离是免费的**：不同 `setting_scope` / `story_id` → 不同 `entity_id` → 不同物理行，改副本不动原库。
- **多世界线兼容**：fork 时连同 `worldline_id` 一并复制（多独立原著按 D10 各自隔离），副本内的世界线与原库一致；可选择性只复制某些原著。

---

## 4. 用户交互（概念层）

建故事时：选择要继承哪些共享原著库（可多选）→ 系统复制副本到该故事作用域。之后故事内"当前知识"的增改都落在副本，原库不变。

---

- 多故事共享同一副本 vs 各自独立副本
